# S2 Viewport

**Status:** wave 1 spike done on Linux (branch `s2/wicked-spike`). Wicked renders the rover headless on lavapipe;
`WickedViewport` passes `ViewportConformance`. Not yet tried on Windows or macOS.

## Current task (wave 1)

Wicked Engine spike: build Wicked as a library from a pinned commit on Linux, render one offscreen frame of the rover boxes in the high-key style, and start a WickedViewport that implements IViewport.

**Check:** A headless test writes a PNG; WickedViewport passes ViewportConformance where it can, with gaps listed in docs/streams/s2.md.

## Blockers

1. **CI does not build the Wicked path yet (S10).** It needs, on a Linux runner: `libsdl2-dev libvulkan-dev
   mesa-vulkan-drivers` (lavapipe), a Wicked checkout at the pinned sha with our patch applied, about 10 minutes
   to build the engine (4 cores), 1 GB disk and about 1 GB RAM per test process. Proposed job:
   `cmake -B build/wicked -G Ninja -DCMAKE_BUILD_TYPE=Release -DFULMETRY_WITH_WICKED=ON -DWICKED_ROOT=...`, then
   `ctest -R viewport_wicked`. Cache the shader cache dir (`FULMETRY_WICKED_SHADER_CACHE`) between runs; cold, the
   first render compiles shaders for 50 s.
2. **`enable_testing()` comes after the module subdirectories in the root CMakeLists (S10).** `app/viewport` calls
   `enable_testing()` itself so its tests register. Moving the root call above `add_subdirectory(app/...)` would make
   that unnecessary.
3. **Not mine, seen while testing:** with `CMAKE_BUILD_TYPE=Release` (-O3) and warnings as errors, GCC 13 reports
   `-Wmaybe-uninitialized` in `app/core/include/fulmetry/core/Events.h:16` (std::variant of events) from
   `app/shell/src/main.cpp` and `app/tests/unit/test_fakes_conformance.cpp`. The `ci` preset (RelWithDebInfo) is
   unaffected. Owner: integrator / contracts.
4. **The vcpkg `full` preset cannot provide Wicked.** There is no vcpkg port; WickedEngine also has no install or
   export rules, so `find_package` is out. We build it from source with `add_subdirectory` (see below).

## Decisions and findings

### Pinned Wicked Engine

- Repo: https://github.com/turanszkij/WickedEngine (MIT)
- Commit: `bee31c0309c03fbf8e793af9fdda253b213685be` (2026-11-07, "impostor buffer grow flickering fix")
- Local patch: `app/viewport/wicked/patches/0001-lazy-object-psos.patch` (15 lines, `wiRenderer.cpp`). See "Memory".

### Build steps (Linux)

```sh
sudo apt-get install -y libsdl2-dev libvulkan-dev mesa-vulkan-drivers   # lavapipe = software Vulkan 1.4
git clone https://github.com/turanszkij/WickedEngine.git ~/deps/WickedEngine
git -C ~/deps/WickedEngine checkout bee31c0309c03fbf8e793af9fdda253b213685be   # a --depth 1 clone needs `git fetch --depth 1 origin <sha>` first
git -C ~/deps/WickedEngine apply $PWD/app/viewport/wicked/patches/0001-lazy-object-psos.patch
cmake -B build/wicked -G Ninja -DCMAKE_BUILD_TYPE=Release -DFULMETRY_WITH_WICKED=ON -DWICKED_ROOT=$HOME/deps/WickedEngine
cmake --build build/wicked -j4                       # about 10 min, mostly the engine
ctest --test-dir build/wicked -R viewport            # conformance + spike PNG
./build/wicked/app/viewport/fulmetry_wicked_spike fixtures/rover/fulmetry.project.json rover.png 640 400 [explode]
```

How it is wired (all in `app/viewport/`):
- `CMakeLists.txt`: default OFF keeps the old INTERFACE target, so fakes-only builds are untouched. ON requires
  `WICKED_ROOT` (cache PATH, the checkout root) and builds `fulmetry_viewport` (static), the spike and the test.
- `wicked/CMakeLists.txt`: `add_subdirectory(${WICKED_ROOT} ... EXCLUDE_FROM_ALL SYSTEM)` with Wicked's editor,
  samples and tests off. It clears our `-Wall -Wextra -Wpedantic` and warnings-as-errors for the engine tree only;
  our own code still builds with them (checked with `-DCMAKE_COMPILE_WARNING_AS_ERROR=ON`).
- Runtime: Wicked compiles HLSL at runtime with `libdxcompiler.so` (shipped in the Wicked repo), loaded from the
  executable's directory; a post-build step copies it there. Compiled shaders are cached in
  `$FULMETRY_WICKED_SHADER_CACHE` (default `/tmp/fulmetry-wicked-shaders/`, 22 MB).
  `FULMETRY_WICKED_THREADS` caps Wicked's job threads.

### Render result

Headless, no `DISPLAY`, no window, no swapchain: `GraphicsDevice_Vulkan(nullptr)` on lavapipe (llvmpipe, LLVM 20,
Mesa 25.2, Vulkan 1.4). Wicked's Vulkan 1.3 feature asserts are compiled out in Release and lavapipe passed them.

- `app/viewport/spike/rover-wicked.png`: assembled rover, 640x400 (39 KB)
- `app/viewport/spike/rover-wicked-exploded.png`: explode 1.0 (39 KB)

High-key look: white background, light grey shading on the white printed parts, saturated part colours from
`Part.color` (sRGB to linear), 1.5 px dark outlines from Wicked's depth outline pass (material outline flag).
Without a trick the background is not white: Wicked's sky is tonemapped (ACES), so a white sky shows as grey,
and a sky bright enough to clip also lights the parts through the environment map and washes them out. So
the sky stays at 1.0 to light the parts, and the final compose clears to white and draws the 3D result only where
stencil != 0 (geometry). The outer half of each silhouette outline falls on the background and is dropped. The
inner half still reads as a dark edge.

### Frame time (lavapipe, 4 vCPU, no GPU)

| | 640x400 | 960x600 |
| --- | --- | --- |
| First `renderToImage`, cold shader cache (device, compile ~380 shaders, init) | 50 s | |
| First `renderToImage`, warm shader cache | 4.1 s | 4.4 s |
| Steady `renderToImage` (4 frames + readback) | 170 ms (≈40 ms/frame) | 300 ms (≈70 ms/frame) |

On a real GPU these should be a few ms. For tests, set `WickedOptions::warmupFrames = 1` to save time.

### Memory: eager pipeline compile, and the patch

Unpatched, Wicked's `LoadShaders()` creates every object pipeline permutation (render pass x material type x mesh
shader x blend x cull x tessellation x alpha test x MSAA, thousands) on background jobs. Each one is a full LLVM
compile on lavapipe. RSS grew about 170 MB/s and the process was OOM-killed at about 14 GB. `FULMETRY_WICKED_THREADS=2`
did not help. The patch passes `nullptr` render pass info for object PSOs when `WICKED_LAZY_OBJECT_PSO` is defined
(our `wicked/CMakeLists.txt` defines it when the patch is present). Wicked's Vulkan backend then compiles each
pipeline on first use. Peak RSS of the spike is now 0.94 GB. On a real GPU eager compile is the better choice (no first-use
hitch). Suggest an upstream option, or define it only for software Vulkan.

### Other findings

- Object pipelines are published at `EVENT_THREAD_SAFE_POINT`, so a one-shot render must wait for
  `wi::renderer::IsPipelineCreationActive() == 0` and fire that event, or it draws only the sky. Without the wait
  the process also crashes at exit: static teardown destroys the device while jobs still use it.
- FAudio logs `FAudio_CreateMasteringVoice` error (no audio device in the container); harmless.
- Wicked keeps global renderer state: one device per process, created on first render (`Engine` singleton).
  Several `WickedViewport`s share it; each has its own `Scene`, `RenderPath3D` and camera.
- If no Vulkan 1.3 device exists, Wicked shows a message box and calls `exit()`, so `renderToImage` cannot return an
  error. Needs a pre-flight device check before we hand it a user's machine.
- Coordinates: Fulmetry is right-handed, Z up, mm. Wicked is left-handed, Y up. Swapping y and z converts between
  them (the swap is a mirror, which is the handedness change); scale 0.01 units/mm.

### Gaps against ViewportConformance and IViewport

`ctest -R viewport_wicked`: all 105 conformance assertions pass, plus a high-key check (white corner, >20 saturated
pixels). Where it is still thin:
- **Picking and projection are CPU math on `Part.bounds`**, the same rules as `FakeViewport`, not the GPU or Wicked's
  scene. Correct while parts are boxes. When S3 supplies meshes, picking moves to `wi::scene::Pick` (ray vs BVH) and
  faces get filled. Projection already agrees with the rendered image because the camera is built from the same basis.
- **Explode and visibility** are honoured in the render (positions, `SetRenderable`). **Selection** recolours the part
  accent red, like the fake. **Hover** is stored but not drawn.
- **X-ray** draws parts translucent (alpha blend 0.25), not tested. **Joints, slice plane and `StageStyle::Realistic`**
  are stored but not drawn.
- `update(dt)` does nothing yet; frames are only driven by `renderToImage`. There is no on-screen path.
- Conformance does not test render fidelity (only "something non-white"). Golden-image comparison is the next check,
  but lavapipe and GPU output differ, so it needs a tolerance or golden images per backend.

### Raven GUI sharing: shared Vulkan device vs native child window

Options for putting the stage inside the Raven GUI window:
1. **Native child window.** Wicked owns a child HWND / X11 / Wayland subsurface / NSView inside the Raven window,
   with its own swapchain. This is what `GraphicsDevice_Vulkan(window)` and `CreateSwapChain` already expect, so it
   is the least code. Costs: Raven GUI cannot draw over the 3D view (comment pins, labels, hover cards) without a
   second overlay window, plus resize and focus juggling on each platform. Wayland subsurfaces and macOS layers
   make it worse.
2. **Shared device, texture handoff.** Wicked renders offscreen (what the spike does) and Raven GUI draws that
   texture as a widget, so overlays come for free. If Raven GUI is Vulkan, the cleanest form is one `VkDevice`.
   Wicked creates its own instance and device and has no "adopt an external device" constructor, so we would
   patch `GraphicsDevice_Vulkan` or let Raven render on Wicked's device. With two devices, share the image through
   `VK_KHR_external_memory_fd` / win32 handles plus an external semaphore. Wicked already enables external memory
   (it has an external-memory VMA pool).
3. **Copy through the CPU** (what `renderToImage` does now): fine for agent renders and tests, too slow for a live
   view (readback costs several ms even on a GPU).

**Recommendation:** use option 2 (offscreen render, Raven GUI composites it). We need to find out from the Raven GUI
side (S5): which graphics API it uses on each OS (Vulkan everywhere, or Metal/D3D?), and whether it can take an
external `VkImage` or import a shared handle. If Raven GUI is not Vulkan on macOS/Windows, use external-memory
interop or, on macOS, Wicked's Metal backend. Fall back to option 1 only if neither works.
