### Mesh convention (changed: was metres, +Y up)

- GLB vertex data is **mm, +Z up, in the part's own frame** (the frame of `bounds`), no root transform, so
  `trimesh.load(meshFile).bounds == bounds`. `asset.extras.fulmetry = {"units": "mm", "up": "+Z", "frame": "part"}`.
  The app applies `placement` and its own Z-up to renderer conversion (S2: scale 1, then your toWicked swap). Generic
  glTF viewers show it 1000x too big and lying down.
- One mesh per GLB, one primitive per material, with POSITION, NORMAL (from the B-rep, smooth within a face, sharp at
  edges) and uint16/uint32 indices.
- Materials: glTF PBR `baseColorFactor` (linear RGB), `metallicFactor`, `roughnessFactor`, `emissiveFactor` for LEDs,
  and `extras.key` / `extras.color` (sRGB hex). The keys are `mesh.PALETTE` (petg-white, tpu-black, pla-red,
  pla-white, servo-blue, pcb-green, steel, brass, gold, chrome, glass, ...). Sources label each child of the
  returned `Compound` with a key; an unlabelled solid gets the manifest colour. `meshes/materials.json` repeats the
  hints per part with triangle counts, sizes and bounds.
- `cad.build` now writes the same kind of GLB (it used build123d's `export_gltf`, metres and +Y up), so a rebuilt
  part and a checked-in fixture mesh are interchangeable. STEP is unchanged (mm, Z-up). The fixture does not check in
  STEP files (`stepFile` stays unset); `cad.build` produces them on demand.

## Installing engines

The base worker needs only Python 3.12+ and jsonschema. Engines are opt-in extras:

```sh
pip install -e 'worker[test]'          # base: CAD tests skip
pip install -e 'worker[test,cad]'      # + build123d (pulls cadquery-ocp wheels, ~150 MB)
cd worker && pytest -q
```

or with pixi: `pixi run -e cad test` inside `worker/` (pixi path not yet exercised). build123d 0.13 installs from PyPI wheels on Python 3.12
and 3.13 (checked on Linux x86-64, Python 3.13). `worker.ping` reports installed engines, e.g.
`{"engines": {"build123d": "0.13.0"}}`.

## CAD source convention

- Part `part:<object>/<slug>` has its source at `<projectRoot>/cad/<object>/<slug>.py`.
  Example: `part:rover/wheel-l` -> `fixtures/rover/cad/rover/wheel-l.py`.
- The file defines `PARAMS: dict` (JSON-serialisable defaults) and `build(params: dict) -> build123d Part`.
  `build` receives `PARAMS` updated by any overrides and returns a valid solid.
- Geometry is in mm, in the part's own frame: the frame the manifest's `bounds` are given in (placement is applied
  by the app, not by the source).
- `sourceHash` = `"sha256:" + sha256(source file bytes + JSON(params, sorted keys, compact))`.
- Outputs: `<projectRoot>/.fulmetry/build/<object>/<slug>.step`, `.glb`, and `.json` (hash, params, bounds).
  Same hash and both files present -> cached result, nothing rebuilt. The .json is written last and removed before
  a rebuild, so a crash never leaves a hash pointing at half-written files.
- Result paths are absolute.
- The GLB is in **mm, +Z up, part frame**, one primitive per material (see "Mesh convention" above; until M1 it
  was build123d's metres / +Y-up export). STEP stays in mm, Z-up. Mesh tolerances: 0.05 mm linear, 0.2 rad angular
  (~350 KB for the detailed wheel).

## Errors

All failures come back as JSON-RPC errors; the worker keeps serving.

| Code | Meaning |
| --- | --- |
| -32602 | params do not match the contract, or the part id is not `part:<object>/<slug>` (lowercase, no `/..`) |
| -32020 | no source file where the convention says (`data.expected` has the path) |
| -32021 | the source failed to load, `build()` raised, or it did not return a valid solid |
| -32022 | build123d is not installed in this worker |
| -32603 | anything else unexpected |

Codes live in `worker/fulmetry_worker/errors.py`.

## Decisions and findings

- Outputs go to `.fulmetry/build/<object>/<slug>.*`, not `.fulmetry/build/<slug>.*`: slugs are unique only within an
  object, and the rover fixture already has `rover/battery` and `remote/battery`.
- The wave-1 wheel (superseded in M1 by the hub + tyre model above): Ø60 x 14 mm TPU wheel, axle along Y, 24 axial tread grooves
  (2 x 1.5 mm) offset half a pitch so lands sit at the ±X/±Z extremes and the tight bounds are exactly 60 x 14 x 60;
  ring pockets on both faces leave a 6 mm web and a Ø12 mm hub; a Ø3 mm N20-style D-shaft bore (2.5 mm across the
  flat, +0.1 mm clearance). Solid volume 23.7 cm³.
- Bounds use `bounding_box(optimal=True)`, rounded to 0.1 µm; the wheel comes out at exactly ±30, ±7, ±30.
- A cold build of the wheel takes about 2.5 s, most of it importing OCP; a cached call takes milliseconds (the source
  is still executed to read `PARAMS`, which is cheap).
- `server.main()` now keeps the real stdout for replies and points fd 1 at stderr, so OCCT/KiCad C++ code that prints
  to stdout cannot corrupt the JSON-RPC stream.
- Sources are executed in-process with full Python: they are trusted project code, like a build script.
