# S5 Workbench UI

**Status:** wave 1 spike done. Recommendation: **keep Raven GUI**, with the conditions under
[Recommendation](#recommendation). Qt 6 stays the fallback.

## Current task (wave 1)

Raven GUI spike: build oscar-soirey/Raven on Linux, open a window with a docked right-hand chat panel, a scrolling message list, a text input and a custom-drawn area; measure frame time.

**Check:** A headless run (Xvfb + lavapipe) takes a screenshot; docs/streams/s5.md scores the four Qt-fallback criteria from the build plan.

### What was built

- `app/ui/spike/workbench.xml`: the shell in Raven XML. A `DockArea` holds the stage (an `Overlay`
  with the custom `<Stage>` tag and two floating panels) and the project chat docked right
  (`DockSize="0.2444"` = 352 px of 1440).
- `app/ui/spike/main.cpp`: registers `<Stage>` as a custom-painted widget (a rotating wireframe rover over
  a 41 x 41 floor grid, redrawn every frame), fills the chat with 50 messages, sends on Enter or the Send
  button, and measures 600 frames after a 60-frame warm-up. Flags: `--font`, `--mono-font`, `--size WxH`,
  `--frames`, `--warmup`, `--run-seconds`, `--empty-stage`.
- `app/ui/spike/run_headless.sh`: Xvfb + lavapipe; types into the composer with xdotool, presses Enter,
  types again, scrolls the list with the wheel, takes screenshots, prints the timings.
- `app/ui/spike/screenshot.png`: the result (quantised to 128 colours to stay under 200 KB, which is why
  the stage backdrop shows bands).
- `app/ui/CMakeLists.txt`: with `FULMETRY_WITH_RAVEN_GUI=ON`, `RAVEN_GUI_ROOT` (cache path) must
  point at a Raven checkout; it is added with `add_subdirectory(... EXCLUDE_FROM_ALL)` (no examples, tests,
  tools or web) and builds `raven_spike`. Raven's own C is compiled with `-w` and without warnings-as-errors.
  OFF (default): nothing changes.

## Fallback criteria

| Criterion | Score | Evidence |
| --- | --- | --- |
| Docking | **Pass** | `DockArea` + `Slot.Dock="Right"` docks the chat on the right; drag-to-redock, tab groups, tear-off windows, `Rdock_area_save_layout`/`load_layout` are built in (Raven's `workspace` example rendered its docked panels under Xvfb; dragging was not exercised in this spike). Measured: chat panel 349 px wide in a 1440 px window. Gaps: size is a fraction (`DockSize` 0..1), not pixels, so the chat grew to 467 px at 1920 wide (we must re-apply 352 px from `Rdock_area_set_changed_callback`/resize or use a `Splitter`); every docked panel has a tab strip, including the stage (the spec has none; a plain `Overlay`+`Splitter` shell would avoid it). |
| Text input | **Pass** | `TextInput` took real X11 key events from `xdotool type` (XTEST): "Make the wheels 70 mm" + Return fired the committed callback (`composer committed: "Make the wheels 70 mm"` in the log), the message was appended, then "typed via xdotool" stayed in the field with the caret (screenshot). Clipboard, selection and undo are in the widget. Gaps (from Raven's README, not tested here): IME composition window placement is not done, and Wayland text-input-v3 (CJK input methods) is not connected. |
| Scrolling chat | **Pass** | `ScrollBox` with 50 wrapped, selectable message bubbles (`Border` + two `Label`s each). `Rscroll_box_scroll_to_end` lands on the newest message; five wheel clicks scrolled up about four bubbles and eight scrolled back to the end (two screenshots). Layout of 223 widgets: 0.010 ms/frame; a whole-tree repaint 0.12 ms. No virtualisation for arbitrary widget rows (only `ListView` text rows are virtual), so a 10 000-message history needs paging or recycling on our side. |
| Custom drawing at 60 fps | **Pass, provisional** | A `Custom` widget painted with `Rdraw_line/rect/circle/text` and invalidated every frame. Raven's CPU cost per frame (layout + paint) is **0.14 ms**, under 1 % of a 16.7 ms budget; everything else is GPU rasterisation. On lavapipe (CPU rasteriser) the full scene ran **18.9 fps at 1440 x 900** (mean 52.8 ms, p50 46.9, p95 99.4, p99 115.0, max 168.5 ms over 600 frames), **62 fps at 720 x 450**, and the UI alone (`--empty-stage`) **95 fps at 1440 x 900** (mean 10.5 ms). Render time scales with pixel count, so it is fill-rate bound: Raven draws each line as an SDF quad over the line's bounding box, so a long diagonal line costs its whole bounding box in fragments. For scale, `vkcube` on the same lavapipe: 3.6 ms/frame. Not measured on a GPU here: re-run `run_headless.sh` on real hardware (see Checks) before calling it final. The real stage will be Wicked rendering into a texture, not `Rdraw_line`. |

## Other findings

- **API maturity: low.** v0.2.2; the first commit was 2026-10-09 (four weeks ago); 231 commits, ~90 % by
  one author; the README says "public API is subject to change". It is moving fast (tags 0.1.2 to 0.2.2 in
  a month) and the code quality is good: C11, opaque generation-checked handles, a render thread, a job
  system, tests clean under ASan/UBSan/TSan, a stable `RInitDesc` that takes new fields. It built first
  time with Ninja, and the spike compiled against its headers with no warnings under our C++20
  `-Wall -Wextra -Wpedantic -Werror` (Raven's own C is built with `-w`). Risk is bus factor
  and churn, not code quality. Pin the commit and wrap it behind our own panel API in `app/ui`.
- **Docs: good for a project this young.** A 70 KB README with a section per feature, `docs/XML.md`
  (every tag and attribute), `THEMES.md`, `ARCHITECTURE.md`, an HTML reference, a Qt-to-Raven guide, and
  headers with a comment on almost every function. The English is idiosyncratic but exact. No
  versioned API reference or changelog per release apart from `ROADMAP.md`.
- **XML and live reload:** worked as described. The `<Stage>` tag came from `Rxml_register_tag`; widgets are
  found by `Name` (`Rwidget_find`); the reload keeps handles, callbacks and typed text of elements that did
  not change, and `Rxml_set_reload_callback` tells us when to look widgets up again.
- **Text, fonts, shaping:** glyphs come from `stb_truetype` with an atlas and subpixel positioning; bidi and
  Arabic joining exist, but there is **no OpenType shaping and no kerning** (README "Not implemented":
  kerning, Indic scripts). **Inter Tight** (Google Fonts variable TTF) and **IBM Plex Mono** loaded with
  `Rfont_create_from_file` and rendered cleanly (screenshot: UI in Inter Tight, the stage caption in Plex
  Mono). A variable font is drawn at its default instance only (no `wght` axis); bold, medium and semibold
  need static TTFs per weight via `Rfont_set_variant`. Fallback fonts and colour emoji come from the system.
- **DPI scaling: works.** With `Xft.dpi: 192` (xrdb) the window reported scale 2.00 and the whole UI laid
  out at 2x with sharp text (checked on a crop). Layout is in logical units throughout. Wayland fractional
  scaling is supported; Windows/macOS per-monitor scaling is claimed but not tested here.
- **Theming to our spec:** `R_LOOK_RAVEN_LIGHT` + `Rtheme_set_accent(red)` + `R_METRIC_CORNER_RADIUS 3` gave
  the high-key white, 3 px, red-accent look with a few calls; per-widget overrides in XML (`CornerRadius`,
  `Background`, `Shadow`).
- **Wicked Engine viewport:** three ways in, by preference:
  1. *Shared device, zero copy*: `Rvulkan_set_external_device(instance, physical, device, queue, family)`
     before `Rinit`, plus `Rvulkan_set_queue_lock_callbacks`, and Wicked's render target shown with
     `Rvulkan_texture_create_from_image_view`. The UI then floats over the stage as the spec needs. Cost:
     Wicked creates its own `VkInstance`/`VkDevice` internally, so S2 must patch or wrap
     `GraphicsDevice_Vulkan` to enable Raven's required extensions
     (`Rvulkan_get_required_instance_extensions`/`_device_extensions`), expose its handles, and take the
     queue lock around its own `vkQueueSubmit`/`vkQueuePresentKHR`. Ordering is by submission on the one
     queue; Raven exposes no semaphores.
  2. *Two devices, shared memory*: `Rvulkan_texture_create_shared` exports an image as an opaque fd that
     Wicked imports. No Wicked device change, but no cross-device sync is exposed (we would see tearing or
     need a fence round-trip on the CPU).
  3. *Native child window* (`Rviewport_set_native`): works with stock Wicked, but Raven "cannot draw over
     or clip that area", so floating panels over the stage are impossible. Not acceptable for this UI.
  So: the device can be shared, but only with a Wicked-side patch. Option 1 is the plan; it needs a spike
  in S2.
- **Headless testing:** works well. Xvfb + lavapipe + xdotool drive the real X11 path. Raven also has a
  null platform and a null backend (`RInitDesc.headless`, `R_BACKEND_NULL`) for unit tests without a
  display. One trap: start Xvfb with `-noreset`, or root properties such as `Xft.dpi` vanish when the last
  client disconnects.

## Recommendation

**Keep Raven GUI.** All four criteria pass on this machine: docking, text input and the scrolling chat
work as specified, and custom drawing is cheap on the CPU side (0.14 ms per frame). The 60 fps result is
provisional until we measure on a GPU. Raven gives us what Qt 6 would cost much more to get: a Vulkan renderer we can
point at Wicked's device (no QRhi/QVulkanWindow interop), one C header and no runtime or licence weight
(Apache-2.0, ~1.3 MB, no moc), XML with live reload for fast iteration on the UI spec, and good
theming for the high-key look.

Conditions, any of which flips the call to Qt 6:

1. Wicked must share its Vulkan device (option 1 above). If S2 cannot patch Wicked for that, the only
   stock path is a native child window, which breaks "everything floats over the stage". Qt would face the
   same problem; this is about Wicked. But it removes Raven's main advantage.
2. 60 fps on a mid-range GPU (an integrated Intel/AMD at 1440p with the chat full and the stage
   animating) must be confirmed with `run_headless.sh` on real hardware in wave 2.
3. Text quality: no kerning or OpenType shaping. Acceptable for an English-first tool at UI sizes; if
   the design needs kerned display type or Indic scripts, we either contribute HarfBuzz shaping upstream or
   switch.
4. Upstream risk: one main author, four weeks old, API not frozen. We pin the commit, keep Raven
   behind `app/ui`'s own panel API (no `Rid` outside `app/ui`), and keep the option to vendor a fork.

## Blockers

- **S10 (root build):** for the `full` preset, Raven needs to come from somewhere other than a manual
  `RAVEN_GUI_ROOT`: either a vcpkg overlay port pinned to `a472444…` or a `FetchContent` in the root
  CMake. `app/ui/CMakeLists.txt` takes `RAVEN_GUI_ROOT` today; it can switch to `find_package(raven)`
  once S10 provides one. Raven is C: the root `project()` stays `LANGUAGES CXX`; Raven's own `project()`
  enables C (works with CMake 3.28).
- **S10 (CI):** a Linux job with `xvfb mesa-vulkan-drivers xdotool imagemagick` could run
  `app/ui/spike/run_headless.sh` as a smoke test (screenshot as an artefact). Not added: it needs the
  Raven source in CI first.
- **S2 (viewport):** Wicked device sharing as above. Needs `GraphicsDevice_Vulkan` to accept extra
  instance and device extensions, expose `VkInstance/VkPhysicalDevice/VkDevice/VkQueue`, and lock its queue
  around submits.

## Decisions and findings

- 2026-11-07: Raven GUI kept for the workbench (spike above). Pinned at `a472444469dd46890e33585e81641309e591fa30`.
- The chat width (352 px) must be enforced by us: `DockSize` is a fraction.
- The stage will not be drawn with `Rdraw_*`; it is a Wicked texture in a `Viewport` widget. `Rdraw_*` is
  for overlays (selection outlines, gizmo labels) and should stay light: each line costs its bounding box
  in fragments.
- Fonts: ship static Inter Tight TTFs (Regular, Medium, SemiBold) and IBM Plex Mono Regular; register the
  weights with `Rfont_set_variant`.

## Checks added

- The default `cmake --preset ci && cmake --build --preset ci && ctest --preset ci` stays green with
