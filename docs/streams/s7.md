## Blockers

- **T3 Code fork** (Alok): needed before `agent/t3code` can be added as a submodule and before the Raven
  provider and the Fulmetry RPCs can land inside it. Nothing else in wave 1 is blocked.
- **Contract change**: applied on `contract/agent-events` (`kContractsVersion` 1, `fulmetryExt` 1). The schema now
  lists the `fulmetry.*` methods in `x-methods` (params and results in `$defs`) and every pushed event under
  `$defs/event`. In C++: `startAgentForComment(comment, render, StartAgentOptions{object, baseRevision, provider,
  commandId})` returns `AgentStarted{agent, thread}`; new `respondToApproval` and `stopAgent`; `ChatRequest::commandId`;
  `AgentCard` gains `pendingApproval`, `stopped`, `provider`, `branch`, `worktreePath`, `revision`; `RevisionSaved`
  gains `parentSha`, `branch`, `agent`, `comment`; `JobProgress` gains `failed`, `agent`. Renders are capped at
  `kMaxRenderSide` (2048 px) and `kMaxRenderPngBytes` (4 MiB). One difference from the wire: `AgentState` keeps its
  four values, because `app/shell` switches over it and a new enumerator would break that build under `-Werror`.
  Wire `waiting` is `Working` with `pendingApproval` set, and wire `stopped` is `Failed` with `stopped` set.
  `agentWireState(card)` gives the wire name. Adding real `Waiting`/`Stopped` enumerators is a later contract change,
  once the shell prints `agentWireState()` instead of switching.
  Follow-ups owed by S7:
  - `app/net` `T3AgentClient`: speak the schema; send `fulmetryExt` in `clientCapabilities` and `fulmetry.subscribe`;
    generate a `commandId` when the caller leaves it empty; encode the render as PNG and refuse one over 4 MiB with
    `render_too_large`. `commentUpdated` carries no anchor or text, so merge it into the project's comment before
    publishing `CommentUpdated`. Pass `agentClientConformance` and, against a supervised fake provider,
    `agentApprovalConformance`.
  - In the fork: implement the six methods and the stream to match `x-methods`, with a test that validates
    recorded frames against the schema.
- **Real Raven run**: not done here. There are no LLM keys in this environment, and installing Raven's Python package
  was not allowed in the sandbox. The skeleton is tested against a fake that copies Raven's wire shapes. First thing in
  M1: run `raven acp` with a key and record a session (see "Open questions").

## Decisions and findings

### 1. Raven: ACP agent — **yes**

Raven implements the agent side of ACP over stdio. An editor (or T3 Code) spawns `raven acp` and speaks
newline-delimited JSON-RPC, protocolVersion 1, on its stdin and stdout.

Evidence, paths relative to the Raven repo at `8448cc62`:

| What | Where |
| --- | --- |
| The `raven acp` command, "Serve Raven as an ACP agent over stdio" | `raven/cli/acp_commands.py` (`acp_app`, line 94), registered in `raven/cli/commands.py:176` |
| Package doc: "Raven as an ACP agent: the stdio channel, and the protocol served over it" | `raven/acp/__init__.py` |
| Method router: `initialize`, `authenticate`, `session/new`, `session/load`, `session/resume`, `session/list`, `session/close`, `session/delete`, `session/set_mode`, `session/set_config_option`, `session/prompt`, `session/cancel` | `raven/acp/methods.py:245-292` (`_route`) |

| Design notes | `docs/specs/2026-08-*-acp-*.md` |

Raven is also an ACP *client* (`raven/acp_client/`, it drives Claude Code, Codex and other agents as sub-agents), and an
A2A server (`raven/a2a/`). Its other programmatic interface is the "Raven TUI RPC": JSON-RPC 2.0 between the Python
parent and its TUI and web UI, 255 methods (`session.create`, `turn.send`, `turn.subscribe`, `session.steer`, ...)
specified in `rpc-schema/openrpc.json`. ACP is the right interface for us: it is the one built for an external host,
and T3 Code already speaks it.

Caveats found while reading:

- The `raven acp --help` text is out of date with the code: it says `session/set_mode` is not implemented and that a
  non-empty `mcpServers` is refused, while `methods.py` routes `session/set_mode` and `capabilities.py` declares
  `raven.mcp.session`, with `_adopt_per_session_mcp` connecting the servers. Trust the code, then confirm with a run.
- `authMethods` is empty: Raven needs its LLM provider configured in its own config (`$RAVEN_HOME`, or
  `raven acp --config <file>`). Fulmetry has to write that config, or pass keys through the environment.
- Raven is Python (>= 3.12) with a large dependency set (`pyproject.toml`, `uv.lock`). Shipping it inside a desktop app
  means bundling a Python runtime; S10 should plan for it (uv-managed venv on first run is the likely path).
- Pre-alpha: the CHANGELOG shows the ACP surface still moving (0.2.x). Pin a Raven version per Fulmetry release.

### 2. T3 Code map

Paths relative to the T3 Code repo at `257e4073`.

**Providers.** A provider is a `ProviderDriver` (`packages/provider-core/src/server/driver.ts`): `driverKind`, a
settings `configSchema`, and `create()` returning a `ProviderInstance` whose `orchestrationAdapter` is a
`ProviderAdapterV2` (`packages/provider-core/src/server/ProviderAdapter.ts`). The adapter's `openSession()` gives a
`ProviderAdapterV2SessionRuntime` with `ensureThread`, `resumeThread`, `startTurn`, `steerTurn`, `interruptTurn`,
`respondToRuntimeRequest`, `readThreadSnapshot`, `rollbackThread`, `forkThread` and an `events` stream of
`ProviderAdapterV2Event` (`provider_session.updated`, `provider_thread.updated`, `provider_turn.updated`,
`message.updated`, `turn_item.updated`, `runtime_request.updated`, `plan.updated`, `turn.terminal`, ...). Everything
is Effect (services, Schema, Stream). Drivers are listed in `apps/server/src/provider/builtInDrivers.ts`.

- **Claude Code and Codex** are built into the server, not packages: `apps/server/src/provider/Drivers/ClaudeDriver.ts`
  and `CodexDriver.ts`, with adapters `apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts` (Claude Agent SDK)
  and `CodexAdapterV2.ts` (Codex app-server protocol, `packages/effect-codex-app-server`).
- **Generic ACP** exists: `packages/provider-acp` (`AcpSessionRuntime.ts` spawns and drives an ACP agent;
  `adapter.ts` `makeAcpAdapterV2(flavor)` maps ACP to `ProviderAdapterV2`; `clientPolicy.ts` answers permission
  requests from the thread's runtime mode), over `packages/effect-acp` (the ACP wire library).
- **ACP agents as packages**: `packages/provider-kiro`, `provider-cursor`, `provider-grok`, ... each supply an
  `AcpAdapterV2Flavor` (launch args, capabilities, steering, model selection, quirks). Kiro is the closest template:
  `kiro-cli acp` (`provider-kiro/src/server/acpSupport.ts`, `KIRO_ACP_ARGS`), steering via its own `_session/steer`.
- **Any ACP agent with no code**: `packages/provider-acp-registry` takes agents from the ACP Registry or a **local
  command** (`settings.ts`: `source: "local"`, `commandPath`, `commandArgs`; spawned in
  `src/server/AcpRegistrySupport.ts:1829-1848`).
- ACP agents get T3's MCP tools as per-session stdio servers (`apps/server/src/mcp/AcpMcpStdioBridge.ts`,
  `provider-acp/src/server/AcpSessionRuntime.ts:2136-2150`), which matches Raven's `raven.mcp.session`.

**Threads, worktrees, checkpoints.**

- A thread (`OrchestrationV2AppThread`, `packages/contracts/src/orchestrationV2.ts:444`) has a provider instance, model
  selection, runtime mode, `branch` and `worktreePath`. Runs, turns, messages and turn items hang off it; state is
  event-sourced into SQLite (`apps/server/src/orchestration-v2/EventStore.ts`, `ProjectionStore.ts`).
- `orchestration.launchThread` takes a `workspaceStrategy` (`orchestrationV2.ts:654`): `root`, `existing_worktree`
  (path), or `worktree` (`baseRef`, `branch`) — T3 creates the git worktree under `<baseDir>/worktrees`
  (`apps/server/src/config.ts:160`, `worktreesDirectory.ts`). The provider session is opened with `cwd` = the worktree.
- Checkpoints are commits of the working tree made with a temporary index and stored as hidden refs
  `refs/t3/orchestration-v2/checkpoints/<scope>/ordinal/<n>` (`orchestration-v2/CheckpointService.ts:26,159`,
  `vcs/GitVcsDriver.ts:905` `captureCheckpoint`, author "T3 Code"). They back turn diffs
  (`orchestration.getTurnDiff`) and rollback. They are not branch commits; a Fulmetry revision is a separate commit.
- Real commits/pushes go through `git.runStackedAction` (`commit`, `commit_push`, ...; `packages/contracts/src/git.ts:18`).

**WebSocket API** (`packages/contracts`): one socket, `GET /ws?orchestrationProtocol=2` (`apps/server/src/ws.ts:3507`,
`contracts/src/environment.ts:13-16`), authenticated with a bearer session token or cookie (`apps/server/src/auth/`). Framing is Effect RPC with JSON
serialization (`RpcSerialization.layerJson`, ws.ts:3574): `Request` frames carrying `id`, `tag` (the method name) and
`payload`, answered by `Chunk` / `Exit` frames; a stream is many chunks. S7 records exact frames from the fork in M1
before writing the C++ client. Methods are in `contracts/src/rpc.ts` (`WS_METHODS`,
line 409) and `ORCHESTRATION_V2_WS_METHODS` (`orchestrationV2.ts:3590`): `orchestration.dispatchCommand` (commands
such as `thread.create`, `message.dispatch`, `run.interrupt`, `thread.metadata.update`), `orchestration.launchThread`,
`orchestration.subscribeShell` (all threads), `orchestration.subscribeThread` (one thread's projection),
`orchestration.getTurnDiff`, plus `server.*`, `vcs.*`, `git.*`, `provider*` methods.

There is **no free-form metadata on threads**, and composer context drops record kinds it does not know
(`contracts/src/composerContext.test.ts:187-206`). Fulmetry data therefore cannot ride in thread metadata as the v0
schema assumed; the fork has to add its own RPCs (below).

### 3. Provider skeleton: `agent/provider-raven`

An ACP client for `raven acp`, laid out like `provider-kiro` (see its README for the file map). `makeRavenAdapter()`
returns the `ProviderAdapterV2` service shape; `openSession()` spawns `raven acp` with `cwd` = the thread's worktree,
initializes, and returns a runtime with `ensureThread` (session/new or session/load, model applied through the
`model` config option), `startTurn` (session/prompt with `appContext` prepended), `steerTurn` (`_raven/session/steer`
when declared), `interruptTurn` (session/cancel), `respondToRuntimeRequest` (answers `session/request_permission`),
and events shaped like `ProviderAdapterV2Event`. Stop reasons map to `turn.terminal` (`end_turn` → completed,
`cancelled` → interrupted/cancelled, `refusal` / limits → failed); the prompt response `_meta` is kept as `nativeMeta`.
It uses Promises instead of Effect so it runs without the T3 workspace; in the fork the Raven specifics become an
`AcpAdapterV2Flavor` for `makeAcpAdapterV2` and the hand-written wire layer is replaced by `effect-acp`.

`test/fake-raven.mjs` is a scripted `raven acp` (same capabilities, ids, permission options, steer and cancel
behaviour, refuses a second concurrent prompt). `test/adapter.test.ts` drives the full lifecycle through it: launch,
initialize, session/new, model switch, a supervised turn that asks permission and edits a file in the worktree,
a declined second turn, full-access auto-approval, steering, interrupt, and close.

### 4. Recommended integration path

1. **M1, no code in T3:** in the fork, add Raven as an `acp-registry` instance with `source: "local"`,
   `commandPath: "raven"`, `commandArgs: ["acp"]`. This proves Raven end to end inside T3 with a real key before any
   provider code is written. Claude Code stays available as the built-in `claudeAgent` instance (the fallback).
2. **M2, `packages/provider-raven` in the fork:** port this skeleton onto `makeAcpAdapterV2` (template:
   `provider-kiro`): capabilities (`supportsActiveSteering`, `supportsModelSwitchInSession`, `supportsMcpTools`),
   `steering` via `_raven/session/steer`, `applyModelSelection` via the `model` config option, permission policy,
   a Fulmetry client icon, settings with `binaryPath` and `configPath`. Register it in `builtInDrivers.ts` and make it
   the default provider instance. Keep this repo's `agent/provider-raven` tests as the fake-Raven suite.
3. **M3, Fulmetry RPCs in the fork** (`fulmetry.*` group next to `WS_METHODS`, implemented as an orchestration
   reactor that reads the same projections the web UI reads), and `app/net` as their C++ client. Steps below.
4. Keep Raven's own sub-agent features (it can drive Claude Code over ACP itself) off for Fulmetry threads at first:
   one agent per comment, with T3 owning worktrees and checkpoints.

Two directions over the same `/ws` socket, as Effect RPC methods in the fork (`fulmetry.*`): requests the app sends,
and one stream, `fulmetry.subscribe`, that pushes events. Compared with `contracts/agent/fulmetry-ext.schema.json` (v0):

`fulmetry.subscribe` stream on T3 Code's `/ws`", add a `fulmetryExt` version (negotiated through T3's

Everything else the app shows (diffs, the transcript) it can read with T3's own `orchestration.subscribeThread` and

### 6. M3: comment → thread → worktree → revision

1. The app posts a comment; `app/net` (`T3AgentClient : IAgentClient`) sends `fulmetry.startAgentForComment` with the
   anchor, text, project root and a render, then publishes `AgentUpdated{starting}` from the reply.
2. The fork's handler dispatches `orchestration.launchThread`: `projectId` = the Fulmetry project (registered by root
   path), `title` from the comment, `modelSelection` on the `raven` instance, `runtimeMode` `auto-accept-edits`
   (edits in an isolated worktree are safe; shell asks), `workspaceStrategy {type: "worktree", baseRef: <current
   revision sha>, branch: "fulmetry/cmt-<id>"}`, `initialMessage` = comment text with the anchor as context and the
   render as an image attachment. It records `commentId ↔ threadId`.
3. T3 creates the worktree and opens the Raven session there (`raven acp`, `session/new {cwd: worktree}`), with
   T3's MCP endpoints and S9's maker-tools bridged in as per-session stdio servers.
4. While the turn runs, a fork reactor projects thread events into `fulmetry.agentUpdated` (step from the latest turn
   item, preview from the assistant message, `parts` from file changes mapped to part ids) and `commentUpdated{working}`;
   approvals surface as `state: waiting`. T3 checkpoints each turn as usual.
5. On `turn.terminal` completed with a non-empty diff: validate through the worker (`project.validate`), commit in the
   worktree (`git.runStackedAction` `commit`), fast-forward the project branch (or leave the branch for review if it
   no longer fast-forwards), allocate the next revision number, then push `revisionSaved {number, sha, changedParts}`,
   `commentUpdated {resolved, reply}` and `agentUpdated {done, revision}`. Failure or refusal → `agentUpdated {failed}`
   and the comment stays open.
6. `reply` dispatches a new message on the same thread and worktree, starting the cycle again from step 4.

M3 check: an integration test that starts the forked T3 server with `agent/provider-raven`'s fake Raven, posts a
comment through `app/net`, and asserts `AgentUpdated` → `RevisionSaved` → `CommentUpdated{resolved}` and a new commit
on the project branch.

### Harnesses (extension v2)

Any T3 Code provider instance can run an agent, not just Raven and Claude Code: `provider` on
`fulmetry.startAgentForComment` and `fulmetry.sendChat` is a `ServerProvider.instanceId`, with an optional `model`
(`models[].slug`). The onboarding screen and the composer's picker (`IAgentClient::harnesses()` and its setup calls)
need no new RPCs; `app/net` maps them to T3 Code's own methods:

| `IAgentClient` | T3 Code |
| --- | --- |
| `harnesses()`, `HarnessesUpdated` | `subscribeServerConfig` → `providers[]` (installed, auth, status, models, setup) |
| `installHarness`, `cancelHarnessSetup` | `provider.install.start` / `.subscribe` / `.cancel` |
| `signInHarness`, `answerSignIn`, `signOutHarness` | `provider.auth.start` / `.subscribe` / `.respond` / `.logout` (browser, device code, credentials, terminal interactions) |
| `setHarnessEnabled` | `server.updateSettings`, `providerInstances[id].enabled` |
| `searchHarnessRegistry`, `addRegistryHarness`, `removeHarness` | ACP registry search and prepare, then an `acpRegistry` instance upsert or remove |

`app/tests/conformance/AgentClientConformance.h` (`harnessConformance`) is the behaviour the real client must match.
